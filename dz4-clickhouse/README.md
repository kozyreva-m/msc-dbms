## 1. Аналитический отчёт по странам

### 1.1 SQL и результат

Запрос в `sql/01_report.sql` (первый блок). Период `[2026-10-20, 2026-10-27)`, порог `played_seconds < 20`.

Полный результат сохранён в `results/01_report_countries.tsv`. Сводка:

| country | events_total | events_under_20 | under_20_percent |
|---------|-------------|-----------------|------------------|
| BR | 208591 | 50164 | 24.05 |
| BY | 412122 | 96784 | 23.48 |
| DE | 365433 | 86748 | 23.74 |
| KZ | 602366 | 141272 | 23.45 |
| RU | 2771858 | 653114 | 23.56 |
| TR | 404729 | 96227 | 23.78 |
| US | 310003 | 73447 | 23.69 |

Цифры сверены с тем же запросом, выполненным по gzip-файлу (до прогона в ClickHouse). На защите подставьте скрин или вывод из `/play`, если ассистент попросит.

### 1.2 Контроль на VALUES

Ручной расчёт для строк из задания (период и порог те же):

| country | events_total | events_under_20 | under_20_percent |
|---------|-------------|-----------------|------------------|
| RU | 3 | 1 | 33.33 |
| KZ | 2 | 1 | 50.00 |

Вошли: RU — 19 с, 20 с, 21 с; KZ — 5 с и 20 с. Не вошли границы периода (19.10 23:59:59 и 27.10 00:00:00). Значение **20** не считается «меньше 20».

Запрос — второй блок в `sql/01_report.sql`; должен совпасть с таблицей.

### 1.3 Ответы

1. **Пример: RU.** За неделю 2 771 858 событий, из них 653 114 короче 20 секунд. Доля `100 × 653114 / 2771858 ≈ 23,56%`: примерно каждое четвёртое **событие** в стране было коротким, независимо от платформы и версии.

2. **События и слушатели.** В контрольном примере у KZ два события у **одного** `user_id` (201): одно на 5 с (короткое), одно на 20 с. Доля **событий** коротких: 1/2 = 50%. Доля **слушателей** с хотя бы одним коротким: тоже 1/1 = 100%, потому что слушатель один. Если бы у другого пользователя было только длинное прослушивание, доля событий осталась бы 50%, а доля «слушателей с коротким» упала бы до 50% при двух разных людях. Отчёт считает **события**, а не уникальных `user_id`.

## 2. Ключ сортировки и чтение

### 2.1 Подготовка

`sql/02_order_by.sql`: таблицы `hw_events_time` (`ORDER BY ended_at`) и `hw_events_country` (`ORDER BY country, ended_at`), по 10 млн строк за 13–26 октября, `OPTIMIZE … FINAL`.

Ожидаемая проверка `system.parts`: по одной активной части и 10 000 000 строк в каждой таблице.

### 2.2 Измерения (заполнить после прогона в ClickHouse)

Четыре запроса: страна DE и все страны за **24.10.2026**, на обеих таблицах. В конце каждого запроса — `SETTINGS` из задания. Для каждого: результат SELECT (должен совпадать между таблицами), **Read rows/bytes** без `EXPLAIN`, фрагмент `EXPLAIN indexes = 1` (PrimaryKey, Granules x/y).

Ориентир по логике семинара:

- Фильтр по **стране + дню**: ключ `(country, ended_at)` отсекает больше гранул, чем только `(ended_at)`.
- Запрос **только по дню** без страны: ключ с `country` первым полем не помогает так сильно; часто выгоднее `ended_at` в начале ключа.

Сводная таблица для README (вставьте свои числа из `/play`):

| Запрос | Таблица | Granules | Read rows | Read bytes |
|--------|---------|----------|-----------|------------|
| DE | hw_events_time | … | … | … |
| DE | hw_events_country | … | … | … |
| Все страны | hw_events_time | … | … | … |
| Все страны | hw_events_country | … | … | … |

Содержательно отчёт за 24.10 (проверка цифр): DE — 59 423 события, 14 833 короче 20 с, **24,96%**; всего за сутки 825 369 событий по 7 странам.

### 2.3 Выводы (шаблон)

1. Сравните granules и Read между таблицами для каждого варианта — сошлитесь с планами.
2. При `(ended_at)` данные упорядочены по времени; фильтр одного дня сужает диапазон. При `(country, ended_at)` внутри страны тоже по времени; равенство по `country` использует префикс ключа.
3. На `hw_events_time` запрос по DE читает меньше **подходящих** строк, чем «все страны», но может прочитать столько же **гранул/строк с диска**, если индекс отсекает только по времени. Меньше событий в ответе ≠ меньше чтения.
4. Для суточного отчёта по одной стране чаще выгоден `(country, ended_at)`; для срезов только по времени — `(ended_at)`. Одного ключа на все отчёты нет — нужен профиль запросов.

## 3. Кодеки

### 3.1 Подготовка

`sql/03_codecs.sql`: 500 000 меток, таблицы `hw_codec_ordered` и `hw_codec_mixed`, три колонки с `ZSTD(1)`, `Delta, ZSTD(1)`, `DoubleDelta, ZSTD(1)`.

### 3.2 Разности

Для **ordered** первые секунды от старта: 0, 1, 2, 3, 4, 5 — первые разности все **1**, вторые разности **0** (идеальная арифметическая прогрессия).

Для **mixed** разности нерегулярны — соседние значения в физическом порядке не идут подряд по времени.

Пример восстановления (ordered): зная базу `2026-10-20 00:00:00` и вторые разности = 0, из трёх подряд секунд восстанавливаются все timestamps.

### 3.3 Размеры

Выполните запрос к `system.parts_columns` из файла. Вставьте шесть строк сжатия в README (ordered/mixed × три колонки). Ожидание: в ordered `DoubleDelta` обычно сильнее всего; в mixed выигрыш Delta/DoubleDelta слабее.

### 3.4 Ответы

1. Сравните `compressed_bytes` по трём колонкам внутри каждой таблицы.
2. Перемешанный порядок ломает маленькие первые/вторые разности → хуже для Delta.
3. **Delta** кодирует разности соседних значений; **DoubleDelta** — разности разностей; **ZSTD** сжимает уже полученный поток байт. Если разности шумные, промежуточный поток не меньше сырого — ZSTD не «волшебствует».
4. Ключ сортировки в задании 2 важен для **чтения**, а не только для сжатия одной колонки. Минимальный размер колонки ≠ минимальный cost типовых запросов.

**Сохранение информации:** исходные `ended_at` с кодеками позволяют считать произвольный интервал (10:15–10:45). Если хранить только дневные агрегаты — гранулярность теряется, такой срез восстановить нельзя.

## 4. Материализованное представление

### 4.1 Подготовка

`sql/04_mv.sql`: источник `hw_mv_events` (10 млн), target `hw_country_hourly` (`SummingMergeTree`), MV `hw_country_hourly_mv`.

После `CREATE MV`: `stored_rows = 0` (инкрементальное MV не обрабатывает уже лежащие строки).

### 4.2 Контроль истории

После `INSERT INTO hw_country_hourly … SELECT … GROUP BY` общий контроль должен вернуть **0 строк**.

### 4.3–4.4 Порции А и Б

**Порция А** (ручной ожидаемый отчёт 27.10 19:00–21:00 после А):

| hour | country | events | short | seconds | % &lt;20 | avg |
|------|---------|--------|-------|---------|--------|-----|
| 19:00 | RU | 4 | 2 | 84 | 50.00 | 21.00 |
| 19:00 | KZ | 1 | 0 | 25 | 0.00 | 25.00 |

**Порция Б** дополнительно: RU 19:00 +1 с (+1 короткое), RU 20:00 10 с; **опоздавшее** событие RU `2026-10-24 12:34:00`, 7 с.

До Б группа **RU, 2026-10-24 12:00** (из полной истории): 26 478 событий, 6 655 короче 20 с, 3 659 184 с суммарно (≈25,13%, среднее ≈138,20 с). После B: **+1** событие, **+1** короткое, **+7** секунд.

`count()` на источнике после Б: **10 000 008**.

### 4.5 Ответы

1. MV срабатывает только на **новые** вставки в `hw_mv_events`; историю один раз залили в target вручную. Событие с `ended_at` 24.10 при вставке 27.10 попало в час 12:00 через MV — поэтому «старый» час меняется.
2. `SummingMergeTree` может держать несколько строк на один ключ до слияния → читаем через `sum` + `GROUP BY`.
3. Две порции в час 19:00 RU: нельзя усреднять проценты порций; нужны суммы событий и коротких (после B в 19:00 RU: 5 событий, 3 коротких → 60%, не среднее 50% и 100%).
4. Для порога **&lt; 10** только target с порогом **&lt; 20** недостаточно: неизвестно, сколько событий имело длительность 10–19 с. Нужны сырые события или заранее заведённые счётчики по корзинам.
