# Домашняя работа 3. Cassandra

Домашняя работа посвящена Cassandra. Кейс: сервис аудита действий пользователя. Каждое действие (вход, покупка или просмотр) пишется в таблицу, приложение читает ленту последних событий. В работе: модель данных и таблицы, вставка и чтение через PreparedStatement, замеры уровней консистентности ONE и QUORUM, сжатие SSTable, bloom-фильтр, TTL и компакция, nodetool repair. Стенд из трёх узлов и контрольные данные настроены; остаётся заполнить заготовку решения, прогнать сценарии и объяснить в README, как это работает и почему решения именно такие.

## 2. Таблица и модель данных

Сервис пишет каждое действие пользователя в таблицу `user_actions`; действие: `login`, `purchase` или `view`. Чтение: лента последних событий пользователя. Контрольный пользователь: `user_id` 1001.

| Таблица | Поля | Типы и ограничения |
|---|---|---|
| `user_actions` | `user_id` | int, partition key, идентификатор пользователя |
| `user_actions` | `event_time` | timestamp, clustering key, время события; порядок по убыванию |
| `user_actions` | `event_type` | text: `login`, `purchase` или `view` |
| `user_actions` | `payload` | text, детали события |
| `user_actions` | сжатие | LZ4 |
| `user_actions_none` | те же поля | та же структура без сжатия; нужна для сравнения размеров в разделе 5 |

Что сделать:
1. Заполните `create_tables` в `solution.py`: обе таблицы, первичный ключ `(user_id, event_time)`, сортировка по убыванию `event_time`, сжатие LZ4 только для `user_actions`.
2. Проверьте схему сценарием `data` (primary key, порядок сортировки, сжатие).
3. Объясните в README: почему партиция по `user_id` и зачем обратный порядок кластеризации.
4. Объясните в README: что произойдёт при двух событиях одного пользователя с одинаковым `event_time`, почему для аудита это риск и как изменить схему, чтобы события не затирались.

## 7. Repair

Что сделать:
1. Выполните `bash ops.sh repair` и убедитесь, что появился файл `results/repair.txt`.
2. Объясните в README:
   - что такое anti-entropy и зачем нужен `nodetool repair`: расхождения между репликами исправляются вне пути чтения;
   - когда без repair не обойтись и что происходит при долгой работе без него: реплики расходятся, чтение может вернуть неактуальные данные, tombstones не подчищаются;
   - чем repair отличается от read repair и hinted handoff: read repair чинит только ключи, затронутые чтением; hinted handoff компенсирует короткие простои узла хинтами.

## Приложение А. Подготовка и команды

Подготовка:
1. Установите и запустите Docker с Compose v2. Для трёх узлов ориентир: от 2 ГБ памяти, доступной Docker; куча каждого узла ограничена 512 МБ. При первом запуске нужен интернет для скачивания образа. Cassandra и языковые среды на хосте не нужны.
2. Положите файлы комплекта в корень проекта: `compose.yaml`, `lab.py`, `solution.py`, `init.cql`, `ops.sh`. Откройте терминал в этой папке.
3. Поднимите окружение и сбросьте keyspace: `docker compose up -d`, `docker compose run --rm lab reset`.
4. Посмотрите данные и эталоны (`docker compose run --rm lab fixtures`), затем заполняйте `solution.py`.

Команды после `docker compose run --rm lab`:

| Команда | Действие |
|---|---|
| `data` | Проверить таблицы, схему (PK, ORDER BY DESC, LZ4) и фикстуры |
| `bulk` | Вставить 10 000 записей через PreparedStatement и проверить чтение |
| `consistency` | Замерить запись и чтение при ONE и QUORUM |
| `compaction` | Настроить TWCS+TTL, проверить TTL по `system_schema` и истечение строк |
| `metrics` | Проверить, что выполнены ручные шаги tablestats и repair |
| `all` | Последовательно выполнить data, compaction, bulk и consistency |
| `reset` | Сбросить keyspace `hw3` и подготовить начальное состояние; прежние результаты проверок очищаются |
| `fixtures` | Показать контрольные данные, параметры и эталоны |
| `shell` | Открыть интерактивный cqlsh для произвольных запросов |
| `help` | Показать справку |

Команды на хосте:

| Команда | Действие |
|---|---|
| `bash ops.sh tablestats` | `nodetool flush hw3`, затем `nodetool tablestats` по `user_actions` и `user_actions_none`; файлы `results/tablestats.txt` и `results/tablestats_plain.txt` |
| `bash ops.sh repair` | `nodetool repair hw3`; файл `results/repair.txt` |
| `bash ops.sh compact` | Принудительная компакция `user_actions` и история компакций; файл `results/compaction.txt` |

Каждый сценарий готовит своё исходное состояние; не запускайте их одновременно и не меняйте контрольный набор. До заполнения соответствующих функций сообщение TODO ожидаемо. Для полного прогона используйте `all`. Скрипт `ops.sh` вызывается через `bash ops.sh`, исполняемым его делать не нужно. Для остановки выполните `docker compose down`. Чтобы удалить и данные в Docker, выполните `docker compose down -v` и повторите подготовку; файлы результатов на хосте остаются.

Настройки:

| Параметр | Значение |
|---|---|
| Cassandra | Образ `cassandra:5.0.4` |
| Топология | Кластер из трёх узлов с данными: `c1`, `c2`, `c3` |
| Keyspace | `hw3`, replication factor 3 |
| Таблицы | `user_actions` со сжатием LZ4; `user_actions_none` без сжатия |
| Компакция и TTL | TWCS окно 1 день, `default_time_to_live` 30 дней (раздел 8) |
| Доступ | Внутренняя Docker-сеть, без аутентификации и TLS; порты на хост не публикуются |
| Контактные точки | Имена сервисов `c1`, `c2`, `c3` во внутренней Docker-сети |
| Подключение | `docker compose exec c1 cqlsh` |
